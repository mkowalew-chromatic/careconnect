# CareConnect patient portal — mobile

The patient portal for iOS and Android, built with [Expo](https://expo.dev) (SDK 57, React Native 0.86, React 19.2 — the same React copy as the web apps) and [expo-router](https://docs.expo.dev/router/introduction/). It uses the same API as the web portal through `@careconnect/api-client`, and its UI comes from [`@careconnect/design-system-native`](../../packages/design-system-native).

Release unit `portal-mobile`, owned by the Portal frontend team. It is not deployed to a VM: a release is a git tag and GitHub Release, and every pull request that touches it gets a Chromatic build on iOS and Android. App-store / EAS distribution is not set up yet.

## What's in it

| Area | Screens |
|---|---|
| Sign-in | Patient login (staff accounts are rejected, as on the web portal); the session token is kept in the iOS Keychain / Android Keystore via `expo-secure-store` |
| Home | Next visit, quick actions, unread-message count |
| Visits | List with stats, pull to refresh · detail with paperwork status, check-in, cancel |
| Messages | Inbox · thread with reply |
| Booking | Visit details → choose a time → your information → review → confirmed (a modal stack; the draft is discarded if you dismiss it) |

## Run it

```bash
npm run api:dev                                     # API on :5000, from the repo root
npm run dev --workspace=@careconnect/portal-mobile  # Expo dev server; press i (iOS) or a (Android)
```

Simulators need Xcode or Android Studio. The default API URL is `http://localhost:5000/api` (`10.0.2.2` on the Android emulator). Set `EXPO_PUBLIC_API_URL=https://<your-host>/api` to use a deployed API. Demo patient: `alice.smith@se-tools.net` (prefilled in development builds).

`ios/` and `android/` are generated by `expo prebuild` and are not committed.

## Storybook

The same app renders Storybook instead of the portal when `EXPO_PUBLIC_STORYBOOK_ENABLED=true`:

```bash
npm run storybook:ios --workspace=@careconnect/portal-mobile      # or storybook:android
```

The scripts pass `--clear`, because Metro caches transforms across the app/Storybook switch. When you switch back, run `expo start --clear` once.

[`.rnstorybook/main.ts`](.rnstorybook/main.ts) loads two story sets:

- **Design System/…** — every component story from `packages/design-system-native`.
- **Screens/…** — this app's screens (`src/screens/*.stories.tsx`), rendered from fixed fixtures in [`src/screens/fixtures.ts`](src/screens/fixtures.ts). Screens are presentational (data and callbacks in, no fetching); the route files under `app/` do the fetching and navigation. That split is what lets every state be a story: empty, loading, error, each booking step.

`.rnstorybook/storybook.requires.ts` is generated (Metro rewrites it on start, or run `npx sb-rn-get-stories`) and committed so `typecheck` works without starting Metro.

## Chromatic

[`.github/workflows/chromatic-native.yml`](../../.github/workflows/chromatic-native.yml) runs on every pull request, push to `main`, and merge-queue ref:

1. **Detect mobile changes** — `turbo ls --affected` says whether this app or anything it depends on changed. If nothing did, the build jobs are skipped by `if:` and still report a conclusion. Chromatic has no TurboSnap for React Native yet, so this is the cost control. The workflow itself has no `paths:` filter, for the same reason as `chromatic.yml`.
2. **Build Storybook (iOS / Android)** — `npx chromatic react-native-build` runs `expo prebuild` and a Release build (`xcodebuild` for the simulator on macOS, `gradlew assembleRelease` on Linux) with Chromatic's Storybook environment.
3. **Visual regression review** — uploads `storybook.app` and `storybook.apk` with `chromaui/action`. Main runs auto-accept and become the baseline; PR changes are reviewed in Chromatic and never auto-accepted.

### One-time setup

1. Create a Chromatic project for this app (separate from the web Storybook and Vitest projects).
2. Ask Chromatic to enable React Native for it (still early access).
3. Add its token as the repository secret `CHROMATIC_NATIVE_PROJECT_TOKEN`.

Until the secret exists, every job skips rather than failing red.

### Stable snapshots

- **Fixtures, not "now".** Fixture dates are local wall-clock times, so days and times render the same in any simulator time zone, and nothing depends on the current date.
- **Animations stop at capture, not skipped.** Chromatic builds the app with `EXPO_PUBLIC_STORYBOOK_DISABLE_UI=true`. `.rnstorybook/preview.tsx` treats that as "capturing" and wraps every story in `<MotionProvider animate={false}>`. Animated components such as `Spinner` (used by `Button loading` and `LoadingState`) then render one fixed frame, so loading states are still snapshotted and diffed. `ActivityIndicator` isn't used, because JS can't control its native animation. The same switch follows the OS **Reduce Motion** setting for users.
- **Status bar.** Captures include the status bar. Component stories render on a padded canvas, and screen stories (`layout: 'fullscreen'`) are wrapped in a top safe-area inset, because screens that live under a navigation header in the app don't pad for it themselves.
- **No modes yet.** Chromatic's modes (dark mode, locale, viewport) aren't supported for React Native, so each variant needs its own story.
